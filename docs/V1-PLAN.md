# Hangzhou Atlas V1 方案

状态：**本地预览已实现，出版核验未完成** · 更新：2026-09-30 · 项目目录：`E:\凌睿\vibe coding\杭州去哪儿`

本文是出版 V1 的执行依据。[原始框架](hangzhou-atlas-framework.md)保留长期构想；实施范围发生冲突时，以本文为准。当前已有地图网页与扩充内容，30 条路线是人工站点示意线，11 条为来源坐标试画曲线；均未达到本文要求的已核验出版轨迹。实际完成内容见 [更新日志](../CHANGELOG.md)。

## 1. 要解决的问题

打开网页后，用户应能在几分钟内回答：“这个周末去哪儿、走哪条路线、沿途有什么、需要多久？”首页直接显示杭州地图与可选路线，不设置宣传首页。

V1 围绕两个正式内容对象：

| 对象 | 用户想知道 | 核心展示 |
| --- | --- | --- |
| 地点 Place | 这里有什么、值得停多久？ | 地图位置、简介、看点、建议停留时间、推荐理由、经过此处的路线 |
| 路线 Route | 这半天怎么走？ | 类型、顺序停靠点、轨迹、参考距离和用时、强度、适合时段、注意事项 |

来源 Source 是两者必备的编辑元数据，也是用户可见的信息：每个地点和路线都能查看出处。合集、个人行程、账户与个人记录留待后续。

## 2. V1 范围和验收

### 页面与交互

- 电脑和手机均以地图为主；路线／地点双视图。
- 站内搜索已收录的地点、路线名称与标签；路线按徒步／逛玩筛选，地点按博物馆、商场、游玩等独立标签筛选。植物园、动物园、游乐园统一用「游玩」主题，具体类型保留在地点分类。参考时长、强度、季节、距离、同行人群等筛选随后按真实内容逐步补齐。
- 点选路线后突出轨迹和编号停靠点；点选地点后展示详情及关联路线。
- 地点与路线详情包含介绍、推荐理由、可以看到什么、时间估计、来源名称与可访问的原始链接，以及最后核验时间。地图内可查看地点；可选保留“去这里／开始导航”入口，不再把“高德查地点”作为主要交互。
- 用户可在浏览器内保存自己的路线草稿并导出文件。其他用户可通过带结构化字段的 GitHub Issue 提交路线建议；维护者核对后合入公共数据。V1 不承诺匿名提交后立刻对所有人可见。

### 首批内容

- **扩充预览：148 个地点、41 条路线（徒步 27、逛玩 14），覆盖 12 个区县。** 此前 100 地点的首批上限已按扩充需求放开。徒步包括西湖沿线、登山短线和老城街巷等以步行为主的路线；逛玩以场馆、商圈和游乐目的地组合为主。地点标签独立于路线类型。出版时逐项核对，不为了凑数发布无法核对的地点或路线。
- 每个地点都要有稳定 ID、名称、所属区县、分类与标签、坐标及坐标系、简短介绍、看点、推荐理由、建议停留时间、推荐指数、来源名称／链接、最后核验时间。优先记录高德 POI ID，并在地图上逐个检查标记落点；同名地点要人工排查。能取得高德 POI 评分时记录其快照与日期，缺失不编造。
- 每条路线至少有类型、起终点、顺序停靠点、参考用时与距离或交通提示、沿途看点、推荐理由、推荐指数、轨迹质量、来源名称／链接、最后核验时间和路线状态。沿途停靠点引用地点 ID，避免出现同一地点多套坐标。路线的「沿途高德评分均值」只由有分数的站点计算并标注样本数，不称为高德路线评分。
- 轨迹质量区分 `verified_track`（有出处的实测或可靠 GPX）、`mapped_path`（沿真实可通行步道／街道整理且人工核对）、`overview_only`（仅站点连线）。出版 V1 的完整路线需达到前两档；`overview_only` 仅作为草稿或明确标示的预览，不计入 10 条出版路线，更不能用于导航。
- 路线状态至少区分 `verified`、`unverified`、`seasonal`、`restricted`、`closed`。未核实或有通行限制的路线不进入默认推荐列表。
- 所有采集内容先作候选，经过名称去重、坐标核对、轨迹核对、来源检查和人工审阅后入库；不把第三方描述或照片原样批量搬运到网站。每个地点、路线的详情卡都展示出处。

### 不在 V1 内

在线多人编辑、匿名内容自动发布、账户同步、数据库、Trip Planner、合集、小红书导入、复杂推荐、自动路径规划、实时路况和天气。后续先核验轨迹、扩充可信内容与细化标签，再评估这些能力。

## 3. 地图与高德接入

V1 以**高德地图 JS API 2.0** 为目标，优先获得杭州本地的地图和地点体验。底图精度与路线轨迹质量是两回事：高德底图不能自动证明徒步轨迹准确，轨迹仍按上一节核验。调用额度对前几版预计充足，但仍在实施前以账号控制台核实认证、额度与计费设置。

需要两类用途不同的凭证：

1. **Web 端（JS API）Key 与安全密钥**：用于网页地图。公开页面可加载 JS API，但安全密钥不能直接写入 GitHub 仓库或 HTML；按高德推荐方式由一个轻量代理保存并转发。GitHub Pages 只发布前端，这个代理需部署在独立服务上。代理提供方、域名及其可用性在实施前确定。
2. **Web 服务 API Key**：供本地或受控采集脚本查询 POI 候选资料。放在本机环境变量或 GitHub Actions Secret，不放进公开网页或数据文件。

高德 JS API 必须在线加载，因此“本地文件方便迁移”指项目文件可复制或克隆；本地预览仍需联网，并可能需通过本地 HTTP 地址及配置的代理访问，不能保证双击 HTML 就能完整显示地图。[JS API 加载文档](https://lbs.amap.com/api/javascript-api-v2/guide/abc/load) · [安全密钥文档](https://lbs.amap.com/api/javascript-api-v2/guide/abc/jscode)

### 配额与费用

高德调用量有限制，具体与账号认证、接口类别和控制台设置有关。据当前[官方计费表](https://lbs.amap.com/pages/base_service_price)，个人认证开发者列出的月配额包括 JS 地图初始化 1,500,000 次、基础搜索 5,000 次；未认证账号对应额度可能为 0，月额度之外可能产生费用。**实际可用额度和 QPS 一律以你的高德控制台为准**，实施前核对账号状态、Key 类型、使用范围和计费设置。

站内搜索首选查询已收录的本地地点／路线数据，这不会在每次键入时调用高德搜索；只在内容采集或确实需要查询未收录地点时使用高德 POI 搜索，以节约额度。[高德地点搜索 API](https://lbs.amap.com/api/webservice/guide/api/newpoisearch)

### 坐标规则

数据要标明坐标系。高德坐标为 GCJ-02；GPS/标准 GeoJSON 常用 WGS84，GeoJSON 顺序为 `[经度, 纬度]`。进入高德地图前统一转换并检查路线和停靠点是否对齐，不能直接混用。[高德坐标转换说明](https://lbs.amap.com/api/javascript-api-v2/guide/transform/convertfrom)

### 出版前核验清单

1. 每个地点至少有一个可追溯出处，记录原始名称、链接与核验日期；高德 POI 可提供位置与部分地点的评分，但标记要在地图上逐个检查是否落在正确入口或景点范围。评分是快照，更新时记录查询日期。
2. 每条路线记录资料出处和轨迹出处；有 GPX 时保留原件或可追溯链接，同时记录坐标系和转换方式。徒步路线手工整理的轨迹也要沿实际可步行道路逐段核对；跨馆区的逛玩连线需明确交通接驳。
3. 检查轨迹是否在杭州目标区域、是否有异常跳点、参考距离是否与路线说明相符、编号停靠点是否贴近轨迹且顺序正确。
4. 核对近期通行信息；关闭、限制进入或不能确认可通行的路段不作为常规推荐。天气和施工会改变实时路况，页面显示核验日期并提示出发前复查。
5. 复核界面展示的来源链接；资料不足时宁可不计入出版数量，也不把示意线写成“实测路线”。

## 4. GitHub Pages、文件和用户提交

`https://<用户名>.github.io/<仓库名>/` 是 GitHub Pages 的**项目网站**地址形式；你给的南京网址符合这个形式，当前工具无法核验该页面的实际内容。[GitHub Pages 地址规则](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

计划将前端和已审核的地点／路线文件放在 GitHub 仓库，由 GitHub Pages 发布。访问者下载 HTML、CSS、JavaScript、JSON 和 GeoJSON，浏览器据此绘制地图。GitHub Pages **不运行后端程序或数据库**；高德安全密钥代理要部署到别处。将来若需要数据库，前端仍可留在 Pages，再连接外部服务。页面与数据的具体发布文件由 GitHub Actions 选取，不将方案文档公开为网站页面。[GitHub Pages 发布方式](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)

项目目录：

```text
README.md、CHANGELOG.md  项目入口与更新日志
docs/                    本方案与长期框架，不作为 Pages 发布源
site/                    网页前端代码与资源
data/                    已审阅的地点、路线、轨迹和来源数据
```

建议的数据文件（实施时再创建）：

```text
data/places.json       地点与坐标、标签、出处引用
data/routes.json       路线属性和顺序停靠点、出处引用
data/tracks/*.geojson  经核验的轨迹；保留原始坐标系说明
data/sources.json      出处名称、原始链接和核验时间
```

地点使用稳定 `id`，路线用 `stops[]` 引用地点 `id`，避免复制多份坐标。文件结构在建库前就是可迁移的数据模型。若未来需要数据库，先导入这些文件，再替换读取层；不要求重做地图视图。正式网页可以构建出便于发布的静态文件，本地保留源数据和完整项目。

**其他用户输入路线时**：GitHub Pages 本身不能替访客安全地写回仓库。V1 提供浏览器内草稿和导出；共享建议通过 GitHub Issue（提交者需 GitHub 账号，仓库需开启 Issues）进入待审核区。维护者检查轨迹、来源和安全提示后更新数据文件，提交 GitHub，Pages 随之更新。以后可用 GitHub Actions 辅助生成待审核 PR，或在需要免 GitHub 账号投稿及网页内管理时引入后端／数据库。浏览器本地草稿只在当前设备，换设备需导出文件。[GitHub Issue 创建说明](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-an-issue)

## 5. 首轮内容获取流程

```text
高德 POI / 杭州文旅与其他公开页面 / 可合法使用的路线轨迹
                  ↓
候选资料：记录来源名称／URL、获取时间、原始名称、坐标系
                  ↓
去重、逐个核对地点落点、核对路线轨迹及停靠点关系、确认通行状态
                  ↓
自己撰写简介、看点和推荐理由；标记核验日期
                  ↓
写入 Place / Route / Source 文件，在地图复核并显示出处
```

自动采集只帮助发现候选，不等于自动发布。使用公开页面和轨迹时遵守其授权、使用条款与标注要求；小红书及更多来源等地图成型后再规划第二轮。

## 6. 后续实施顺序

1. **已完成各区扩充预览**：128 个地点、33 条有来源的路线（徒步 19、逛玩 14），覆盖 12 个区县；地图、站内搜索、区域与主题筛选、地点分类颜色、评分、详情与本地高德安全密钥代理已运行。路线线形均为 `overview_only`，其中一条试用来源坐标，界面明确标为非导航轨迹。
2. **下一步内容核验**：逐个检查地点标记；逐条核对路线停靠点、实际道路／步道、参考距离与近期通行情况。取得可靠轨迹或完成逐段核对后，才升级路线质量状态。
3. 完成本地路线草稿、导出和 GitHub Issue 投稿入口；检查手机体验与状态提示。
4. 决定公开版的高德密钥代理、域名和 GitHub 仓库。达到出版数量与质量门槛后再发布 GitHub Pages，记录访问地址。
5. 每轮在 [CHANGELOG.md](../CHANGELOG.md) 记录已完成、已核验的增改。

### V1 完成标准

用户能在高德地图上按区域和主题查询**有出处的地点**，打开**至少 10 条有出处、已审阅且有真实可核对轨迹的路线**（同时包含徒步与逛玩），看到沿途地点并据此判断时间、强度和看点。每个地点标记已人工复核；每条轨迹和停靠点关系已检查；未核实路线不作正常推荐。地图在目标部署环境可用；公开仓库没有安全密钥；README 能让人在另一台电脑上接手项目。
